# Фотографии проектов: локальная реализация

Обработка запускается при выборе JPG/PNG/WebP в редакторе проекта. Оригинал до 30 МиБ и 100 Мп сохраняется без изменений. Web Worker декодирует ориентацию EXIF и создаёт WebP quality 0.85: thumbnail 600×450 (для маленьких исходников — меньше), content до 1600 и large до 2400 по длинной стороне. Прозрачность сохраняется; canvas не переносит EXIF/GPS в производные. Воркер требует современный браузер с OffscreenCanvas и createImageBitmap. Выбор и оптимизация локальны; загрузка начинается по сохранению проекта.

## Хранение и повторное использование

Используется существующий приватный bucket project-media и project_media. Одна фотография — одна запись kind=image: path является архивным original_path, variants содержит thumbnail/content/large пути. Пути: projectId/mediaId и projectId/mediaId/{thumbnail,content,large}.webp. Запись содержит исходное имя, MIME, размер, ориентированные width/height, created_at, alt и caption. Подписи отдельных вхождений остаются в блоках.

В разделе «Фотографии проекта» можно повторно добавить снимок в текущую вкладку или выбрать «Использовать как обложку». Оригинал повторно не загружается. Для совместимости cover_media_id указывает на отдельный технический файл кадра kind=cover, а cover_original_id — на запись исходной фотографии. Это производная обложка, не вторая фотография в пользовательской медиатеке. Каждый новый кадр получает UUID; исходные файлы и старые кадры не перезаписываются и не удаляются. Область хранится в projects.cover_crop. Снимок остаётся в исходных блоках/галерее.

Существующая модель ограничивает медиа одним проектом. Повторное использование внутри проекта реализовано; выбор чужих фотографий между проектами не добавлен. Ограничения FK и проверки сохраняют изоляцию проектов. Автоматического удаления Storage при удалении проекта нет, поэтому общие/архивные объекты не удаляются. Для будущей общей библиотеки понадобится отдельная модель связей; текущую изоляцию ради этого не ослабляем.

Старые записи без variants сохраняют прежнее отображение. Будущая пакетная оптимизация должна читать исходник только под администратором, создавать производные под новыми UUID, явно переключать ссылки после успешной загрузки и сохранять старые объекты. Автоматический backfill и обработка при каждом просмотре не запускаются.

## Выдача посетителям

Карточка получает thumbnail, статья — content, увеличенный просмотр загружает large по клику через Storage с RLS. Старые изображения используют прежние пути. Для content и карточек используются временные signed URLs (120 секунд), изображения статьи имеют loading=lazy, decoding=async и размеры. На сервере приложение обновляет ссылки при периодическом обновлении данных (60 секунд), возврате фокуса и видимости. Уже выданный signed URL действителен до истечения срока после снятия с публикации; новые подписи выдаются только при разрешении RLS. Уже загруженные посетителем данные отозвать нельзя.

Новые архивные оригиналы недоступны посетителям даже у опубликованного проекта. Доступ к ним есть только у администратора. Производные не публикуются до финального сохранения ссылки из блока/обложки. Запись старого опубликованного снимка при staged upload сохраняется. Повторное сохранение после сетевой ошибки использует неизменяемые UUID и не удаляет файлы.

Обложки категорий сохраняют существующий отдельный механизм category-covers и его ограничения; миграция их не затрагивает.

## Применение и лимиты

Миграция: supabase/migrations/004_image_variants.sql. Она повторно безопасна, сохраняет данные и старые политики, поднимает только лимит project-media до 31457280 байт, дополняет таблицу и функции проверки/сохранения. Не применена к облачной базе. До её применения новый протокол сохранения не готов к работе с облачной БД.

Supabase CLI отсутствует в текущем окружении. SQL проверен реальным PostgreSQL через PGlite вместе с миграциями 001–003. Проверку через CLI выполнить в отдельном тестовом Supabase проекте/локальном стеке, предварительно посмотрев `supabase migration list --local`. Не выполнять reset или db push для связанной production-базы. После резервной копии и отдельного подтверждения можно запланировать облачное применение.

Дополнительно проверить Storage Settings → Global file size limit: bucket не может превышать глобальный лимит. Free допускает глобальный лимит до 50 МБ, поэтому 30 МБ не требует платного тарифа. Глобальные настройки аккаунта здесь не проверялись и не менялись. Используется прежний standard upload; для файлов более 6 МБ Supabase рекомендует TUS для устойчивости. Текущий способ принимает 30 МБ при достаточном глобальном лимите, а при сбое позволяет повторить сохранение; возобновления с середины файла нет.

Источники: https://supabase.com/docs/guides/storage/uploads/file-limits и https://supabase.com/docs/guides/storage/uploads/standard-uploads.

## Проверки

`npm run build` — существующие регрессии, новый сценарий повторного использования обложки, миграция 004, приватные оригиналы и черновики, 30-МБ запись, недопустимые пути, повторное применение и сохранность категорий. happy-dom использует подставной Worker/Auth/Storage.

`node tests/image-optimizer-browser.mjs` — отдельный реальный headless Chrome на macOS с временным профилем и локальным HTTP-сервером: worker, JPG 18 МиБ, вертикальный/горизонтальный/квадратный кадр, PNG alpha, маленькое изображение, EXIF rotation, лимиты и неверные форматы. Используются синтетические изображения (18-МБ JPEG дополнен хвостовыми байтами); проверка размеров, декодирования и неизменности оригинала автоматизирована. Художественное качество реальных фотографий и реальная облачная загрузка требуют ручной проверки на тестовой базе. Production и Vercel не менялись.
