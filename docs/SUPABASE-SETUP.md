# Supabase: настройка и проверка A45-New

Статус: пользователь сообщил о применении 001/002 и назначении администратора в Supabase. Проверкой публичного API подтверждены 45 категорий, 7 корней, исходные ID/slug/parent_id, отключённая регистрация и ответ false для анонимного is_a45_admin. Публичный endpoint Storage подтверждает существование category-covers. Фактические значения его лимитов и установленные политики требуют результата read-only 05_diagnostics.sql либо 04_verify.sql. Реальный вход и загрузка администратором пока ожидают ручной проверки в браузере. Vercel не обновлялся.

## 1. Проект и переменные

Целевой проект `slajmofddtelskhpjlpa` выбран пользователем как будущая production-база. Отдельного тестового проекта пока нет. Проверки SQL выполняются локально; облачные изменения — только вручную после подтверждения порядка действий. Не передавайте пароль базы, пароль администратора, `service_role` или `sb_secret_...` в чат, Git или клиентские переменные.

В Project Settings / Connect возьмите Project URL и publishable key (либо старый `anon` JWT). Создайте локальный `.env.local`, сохранив уже имеющиеся служебные переменные Vercel:

```dotenv
SUPABASE_URL=https://<PROJECT_REF>.supabase.co
SUPABASE_PUBLISHABLE_KEY=<PUBLIC_PUBLISHABLE_KEY>
```

В показанном примере стоят шаблоны. Предоставленные пользователем реальные URL и публичный ключ уже сохранены локально в исключённом из Git `.env.local`; в документацию они не копируются. Сборка выбирает только эти два значения, проверяет тип ключа и отклоняет secret/service_role. URL и публичный ключ могут быть в клиенте; права задаются RLS. Остальные переменные окружения в bundle не копируются. `.env.local` исключён из Git и загрузки Vercel.

## 2. Ручное применение схемы после подтверждения

В SQL Editor последовательно выполните:

1. `supabase/migrations/001_categories.sql`.
2. `supabase/migrations/002_seed_categories.sql`.

Перед миграциями выполните read-only запрос `supabase/manual/00_preflight.sql`. Если обнаружены ранее созданные таблицы A45 или bucket без журнала миграций, остановитесь для разбора существующей схемы.

Миграция 001 применяет схему один раз в транзакции и записывает версию в защищённую `private.a45_schema_migrations`. Успешный повторный запуск — без изменений. Одновременные запуски сериализуются advisory-lock. Если найдены чужие объекты с совпадающими именами, транзакция прерывается, не перезаписывая данные. Повторный запуск не предназначен для исправления вручную изменённых политик или схемы: такие случаи требуют отдельного аудита.

Миграция 002 использует `ON CONFLICT (id) DO NOTHING`: не меняет ранее отредактированные названия, связи, обложки и даты. Коллизия slug с другим ID приводит к откату, а не замене записи.

Будут созданы:

- `public.categories`: id, parent_id, slug, title, description, cover_image_path, sort_order, created_at, updated_at; дополнительно `is_published` для политики чтения.
- `private.a45_schema_migrations`: журнал применённой версии без клиентских прав.
- `private.site_admin`: единственный доверенный UUID администратора; приватная таблица с RLS и без прав клиентского доступа.
- Функции и триггеры проверки администратора, публикации предков, запрета циклов и обновления updated_at.
- Публичный Storage bucket `category-covers`, лимит 5 МБ, MIME: image/jpeg, image/png, image/webp; отдельные политики SELECT/INSERT/UPDATE/DELETE для администратора. Дополнительные restrictive-политики не позволяют более широким Storage-политикам обходить ограничения этого bucket; права других bucket не меняются.
- Все 45 имеющихся категорий, включая 7 корней, с исходными ID, slug, parent_id и порядком. Проекты остаются в JavaScript, их categoryIds и URL не изменяются.

API не разрешает создание/удаление категорий или редактирование родителя, slug и порядка. Текущий редактор меняет только title, description и cover_image_path. При будущих структурных изменениях SQL проверяет циклы и сериализует записи структуры. Для чтения публичной категории должны быть опубликованы и она, и её родители.

## 3. Единственный администратор

В Authentication → Providers / Sign In settings отключите публичное создание пользователей и анонимный вход. В Authentication → Users вручную создайте одного пользователя с email и паролем; подтвердите email через Dashboard. Пароль вводится только в Supabase и форме входа, не в исходных файлах.

Скопируйте его UUID из Authentication → Users. Откройте `supabase/manual/03_assign_admin.sql`, замените `<ADMIN_USER_UUID>` и выполните весь файл. Он проверяет существование и подтверждение email, не заменяет другого администратора и безопасен при повторном назначении того же UUID. Не создавайте Auth-пользователя прямым INSERT в auth.users.

Таблица допускает только одного администратора. Клиент не может добавить себя в неё или изменить свой статус. Права проверяются серверной функцией `is_a45_admin()` и RLS; другие авторизованные пользователи остаются без права изменения категорий и Storage.

Укажите Site URL для тестового сайта и затем для production: `https://a45-new.vercel.app`. Используется вход email/password, без публичной регистрации, magic links или OAuth. Не включайте автоматическое применение непроверенных миграций при каждом деплое.

## 4. Локальная проверка

```sh
npm ci
npm run build
npm run preview
```

Откройте `http://127.0.0.1:3001/admin` (или `/#/admin`). Если порт занят, выберите другой. Обычный Python-сервер не делает rewrite для `/admin`: локально используйте hash-ссылку. В Vercel `/admin` направляется на index.html через vercel.json; `/#/admin` также поддерживается.

1. Без входа отображается форма входа; неверный пароль не открывает редактор.
2. Обычный Auth-пользователь без строки private.site_admin видит отказ в доступе.
3. Администратор видит список всех категорий и редактор title/description/обложки.
4. Выберите JPG/PNG/WebP до 5 МБ. Файл сначала проверяется по MIME, размеру и сигнатуре, затем декодируется браузером. SVG не принимается; разрешение ограничено 40 мегапикселями.
5. До «Сохранить» в облако ничего не отправляется. Масштаб и горизонтальное/вертикальное положение задают кадр 4:3; preview и сохраняемый кадр используют одну геометрию.
6. После сохранения загружается очищенное canvas-изображение 1200×900, обычно WebP, с уникальным UUID в пути `category-id/uuid.webp`. В таблице хранится только путь.
7. Название, описание и путь сохраняются с проверкой предыдущего updated_at. При конфликте/ошибке обновите список и проверьте результат: новый файл при неопределённом сетевом ответе не удаляется, чтобы не сломать возможно уже сохранённую ссылку.
8. Ранее загруженные файлы сохраняются: текущая версия не удаляет их автоматически. RLS дополнительно запрещает удаление файла, на который ещё ссылается категория. Неиспользуемые файлы можно позднее проверить и удалить вручную через Storage, отдельно от сохранения карточки.
9. Откройте главную в другой вкладке/приватном окне. При фокусе страницы или в течение 60 секунд обложка обновится без Git-коммита и нового деплоя. Перезагрузка получает данные сразу.
10. Повторите замену; проверьте проектные страницы, вкладки, дерево и старые URL.
11. Выйдите; проверьте, что форма редактирования больше недоступна.

Если Supabase не настроен или временно недоступен, главная использует существующие локальные данные. При успешном ответе главная отображает корневые категории, прочитанные из Supabase; без cover_image_path остаётся локальная SVG-обложка. Структура дерева и демонстрационные проекты остаются локальными на этом этапе. Автосоздания новых категорий из админки нет.

## 5. Серверная проверка прав после ручного применения

Сначала выполните read-only `supabase/manual/04_verify.sql`: при начальном наполнении ожидается 45 категорий, 7 корней, максимальная глубина 5, включённый RLS и один назначенный администратор. Затем отдельной проверкой проверьте:

- Роль anon читает опубликованные категории, но не черновики и не потомков скрытого раздела.
- anon и authenticated без admin UUID не могут обновлять категории или загружать объект в category-covers.
- Администратор может обновлять только разрешённые поля.
- Попытка изменить parent_id через клиент отклоняется даже администратору.
- Прямая циклическая связь и цикл через 5 уровней отклоняются.
- Storage не принимает SVG, запрещённый bucket, неправильный путь и файл больше 5 МБ.
- Через SQL или Dashboard нельзя случайно назначить второго администратора.

Локальный `npm test` выполняет реальные PostgreSQL-проверки схемы/RLS, тесты границ загрузки, геометрии кадрирования, отклонения секретных ключей, порядка сохранения/очистки и прежние тесты сайта. Это не подмена облачных проверок Auth/Storage и браузера. В Vercel админку не публиковать до реальных проверок Auth/Storage. Применение схемы к будущей production-базе пользователь отдельно подтверждает; миграции автоматически не выполняются.

## 6. Первый production-запуск — после успешной проверки

Примените проверенные миграции в целевом проекте Supabase, создайте администратора и настройте Auth. В Vercel → a45-new → Settings → Environment Variables задайте SUPABASE_URL и SUPABASE_PUBLISHABLE_KEY для Production. Не добавляйте service_role. Один раз опубликуйте проверенную версию frontend. Затем `/admin` будет доступен на `https://a45-new.vercel.app/admin`.

Переменные являются build-time конфигурацией: изменение самого подключения требует сборки/деплоя. После первоначального подключения загрузка и замена фотографий меняют только PostgreSQL/Storage и **не требуют** ни нового коммита, ни деплоя.


## Порядок действий в Dashboard для текущего проекта

1. Откройте https://supabase.com/dashboard/project/slajmofddtelskhpjlpa и проверьте выбранный проект.
2. Authentication → Sign In / Providers → выключите **Allow new users to sign up** и **Allow anonymous sign-ins**, сохраните. Email/password provider оставьте включённым — это вход существующего администратора. Публичный сайт использует роль anon без Auth-сессии и не нуждается в регистрации; это не то же самое, что Anonymous Sign-Ins в Supabase Auth.
3. SQL Editor → New query → роль postgres: сначала 00_preflight.sql. Проверьте результаты, при неожиданных объектах остановитесь. Для базы с существующими важными данными перед DDL сохраните их экспорт/резервную копию доступным вам способом.
4. После подтверждения: отдельным запросом вставьте полный 001_categories.sql, Run. Он должен завершиться целиком. Если ошибка — не запускайте 002, сохраните текст ошибки и остановитесь.
5. В новом запросе выполните полный 002_seed_categories.sql. Категории должны сохраниться со своими исходными ID и parent_id.
6. Authentication → Users → Add user → Create new user: ваш email, уникальный пароль, Auto Confirm User — включено. Пароль остаётся только у вас. Скопируйте UUID созданного пользователя.
7. Выполните 03_assign_admin.sql с подставленным UUID. Это назначение прав существующему Auth-пользователю, а не включение регистрации.
8. Выполните 04_verify.sql. В Storage должен появиться category-covers с Public и лимитом 5 МБ.
9. Authentication → URL Configuration → Site URL `https://a45-new.vercel.app`. Настройки Vercel и публичный frontend сейчас не меняйте.
10. Сообщите, что шаги завершены, и результаты read-only проверки без паролей/секретов. Далее отдельно проверим локальный вход, загрузку и RLS реального Supabase, прежде чем публиковать админку.

Документация: [Auth configuration](https://supabase.com/docs/guides/auth/general-configuration), [Users](https://supabase.com/docs/guides/auth/users), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).


Локальный preview (`scripts/preview.mjs`) обслуживает только dist, поддерживает /admin и блокирует доступ к dotfiles. Он не является backend приложения и не получает пароль: браузер обращается к Supabase Auth напрямую. Порт меняется через A45_PREVIEW_PORT. Для единого результата RLS/Storage выполните `supabase/manual/05_diagnostics.sql` в SQL Editor с ролью postgres — запрос только читает настройки, без паролей и ключей в ответе.
